## 与图谱一起使用

- 按上游流程完成代码/领域/知识图谱；工程任务同时解释目标 → 机制与假设 → 实现/有效配置 → 实验 → 结论 → 改进入口。只加入实际查证的连接。
- 文件依赖说明实现结构；是否有效必须关联实验。区分外部声明、源码确认、运行验证、推断和待验证；源码存在或图谱校验通过不代表功能已验证。
- 在现有 node summary、tour、document/config/resource 节点及上游允许的关系中呈现必要证据；不要求修改 schema。原始记录和主要解释仍保留在项目既有文档/运行目录，通过图谱导航到它们。
- 导览顺着用户问题讲：解决什么、输入输出、为什么这样设计、证据是什么、修改哪里会影响哪些结论。首次展示突出关键层次，详细文件/函数关系保留在上游图谱中供展开。
- 按上游 freshness/incremental 流程更新图谱；同时检查受影响解释与验收条件。只更新相关主题，不把每次分析变成全库文档重写。
- 普通 Markdown 工程文档不自动视为 Karpathy wiki；调用 understand-knowledge 时遵循其格式检测与提示，不为工具擅自重排原文档。

# 工程理解与项目知识维护（Understand Anything 补充）

## 目标

帮助用户理解与解释系统的机制、证据和设计取舍，知道怎样改进并继续验证，随时找到当前状态与关键阶段产物。汇报、学习、开发、复现和交接都是使用场景；不要只站在陌生接手者角度，也不要变成论文综述或调试流水账。

输出层次：对话讲增量或直接回答当前问题；项目文档保持当前可独立理解的全貌；代码、配置、实验记录保存具体证据。简明与必要性兼顾，删除冗余而不是删除因果、条件和证据。

## 选择工作范围

先确认本次目标、已有约定和允许的执行范围，读取项目知识入口及相关状态，再按需查证。用户提过的词不等于已掌握；用户已接受的前提不需要每轮重论证。

普通任务只做受影响内容的增量维护；明确的初始化、审计、历史整理或汇报任务才检查更广范围。优先复用已有文档、实验追踪工具和目录，不先造框架、不重构无关代码、不预建一堆空白页面。

按需阅读：
- 文档树、理论/工程说明、状态与待办：`references/workspace.md`。
- demo、代码、文档等产物的命名、分层与证据：`references/artifacts.md`。
- Dashboard 启动与 Demo 文件通过本机 VS Code 打开的约定见 `../../understand-dashboard/SKILL.md`，使用其中的启动脚本与共享 viewer 实现。
- 数百个历史输出的安全整理：`references/legacy-cleanup.md`。
- 模板位于 `assets/`；仅拷贝真正需要的模板，不复制所有占位文件进项目。
- 无现成索引工具时，可用 `scripts/catalog.py` 生成只读盘点和精选入口；它不评估结果质量，也不运行仿真。

## 提取值得保留的理解

沿本次目标的一条实际链路调查，例如入口 → 生效配置 → 资产/预处理 → 状态/动作接口 → 仿真 → 检查与输出。不要止步于模块或文件名称。

优先检查影响结果或修改方案的隐含条件：覆盖后的实际配置、坐标/单位、数据布局与时序、动作来源和控制语义、物理参数与数值设置、本地补丁、固定资产假设、验证指标含义。按影响取舍，清单不是必须填满的表。

重要发现用自然语言串起：机制/理论 → 当前实现位置 → 结果或取舍 → 证据 → 必要的改进入口。问自己：用户能否据此解释“为什么这样做”？改变资产/任务/条件时，应该从哪里改？哪个最小实验能区分当前的猜测？不要把每项未知都升级成大型科研计划。

理论笔记仅解释与项目问题相关的定义、关键假设、变量/单位和必要推导，并映射到代码与可观测结果。说明理想模型与本项目近似/简化的区别，引用可定位的论文/官方文档；不编写无关百科，不为凑深度推导整章。

向上汇报保留“做了什么、为什么、证据、适用范围、下一步/需要决策”的短说明，随后链接依据。尤其区分借用的上游能力、本地修改、实际验证和待检验推断，不美化为未经证实的能力。

## 留存证据与状态

关键事实区分外部声明、源码确认、实际运行与推断。源码引用路径和符号/配置键，必要时附 commit；运行事实引用记录与输出；外部资料记录版本或查阅日期。没有证据就写清具体缺口，不编造结果、位置或完成状态。

关键运行留存足以解释和恢复条件的最小元数据：代码版本及相关未提交差异、实际配置、资产标识、命令与工作目录、相关环境/后端、种子、产物路径和已执行检查。完整原始内容保留在原文件，不复制进多篇文档；敏感凭据不采集，受限资产只记录合法获取入口。

进程完成、数值检查、视觉检查与任务指标分别记录已做范围；没有观看的视频不标记视觉通过。精选展示只代表选择用途，不自动代表可复现或实验成功。批量验证记录样本与检查范围，不把一个样例的结果推广到全部。

重要失败只在影响解释、复现、方案选择、改进或避免昂贵重试时突出。写明条件、证据、影响和重试触发条件；旧结论未变则链接，不反复免责声明。

## 更新知识而非堆积报告

按 `references/workspace.md` 把事实放到一个主要维护位置；修改已有内容、补链接、合并重复。当前状态不是实验日志；任务列表不是想法垃圾箱；产物索引不是文件系统全文转录。

在关键实验、重要事实/决策、接口/条件改变时及时落盘，任务结束前检查受影响的入口。需要较长时间的已获授权任务，可在中间关键节点记录恢复所需状态，但不要每条消息触发整树重写。

用户允许对被更充分证据覆盖的旧结论直接缩减或替换；有追溯价值才移入项目归档并保留简短索引，不为每次改写保存全文副本。仅较新或增加候选不构成严格优于；不同目标下仍有效的结论可以降为备选。此约定不等于删除原始运行证据。

新证据替换旧结论时保留必要的演变和证据关系；关联实现改变但未复核时，将相应结论标为待复核。不要通过刷新日期制造新鲜感。已完成任务需有结果/验收入口；探索建议与用户已接受的待办分开。

命名与目录按 `references/artifacts.md` 维护。整理历史文件先盘点、索引和关联来源，再考虑移动；不要为整齐而破坏原始引用和复现路径。

独立文档默认指独立于聊天的持久文件，优先仓库内可版本化文档；外部知识目录须有稳定仓库标识与路径映射。网页/协作平台可作为查看或发布视图，指定主要维护来源，不双写漂移。只有有权限并获授权时才同步，不把本地完成说成已外部发布。

## 验收

按本次范围检查，不每轮强制全做：
1. 理解：能否解释关键机制、理由、条件和证据，而非只复述名词？
2. 改进：能否定位一个具体修改入口或一个有判别力的下一步实验？
3. 查阅：能否从统一入口找到当前状态、最高价值待办和相关主题，不翻历史聊天？
4. 产物：能否找到一个指定阶段的代表结果，说明选择理由、验证范围，并追到代码/配置/运行记录？
5. 简明：是否删除了重复结论、过时状态和无价值章节，同时保留必要背景与证据？

缺口优先通过定点读代码、查记录或获授权的最小验证弥补；资料不足就标记缺口，不用写长文替代调查。回复只给本次有价值变化、可直接打开的入口和确实需要用户决策的事项，不凑固定条数。

本 skill 不授予删除/外传、批量改名、修改共享权限、重装环境或额外大型实验的权限；不承诺会话关闭后的无人值守维护。

### 执行取舍
先做有判别力的调查，再选择简单可验证的实现；避免围绕低价值方案反复修补。独立调查可交给 subagent 并行完成，遵循 Understand Anything 的分工与当前工具可用性。
